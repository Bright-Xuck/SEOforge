# Sprint 21 Plan — Structured Content Patching Engine (v0.21.0)

## Goal
Build `@forge/dom-engine` so Forge can apply precise, targeted content changes to Elementor JSON trees, Gutenberg block grammar, and arbitrary HTML — without replacing whole pages.

## Scope
- New package `packages/dom-engine/`
- Format detection (Elementor / Gutenberg / generic-HTML)
- Tree patching for structured formats
- DOM patching for generic HTML
- Preview with honest fidelity reporting
- CLI commands: `forge dom map|preview|patch|validate|inspect`
- Integration with existing execution engine (no WordPress plugin work this sprint)

## Out of Scope This Sprint
- WordPress REST endpoints for `_elementor_data` read/write
- Live Elementor rendering / browser automation
- Repeater/nested-widget targeting in Elementor
- Gutenberg dynamic-block rendered preview (falls back to structured diff)

## Dependencies
- `@forge/core` — `WriteProvider`, `WriteOperation`
- `@forge/content-intelligence` — `SectionKind`, `PageDNA`
- `@forge/content-generation` — `ContentPatch`, `GeneratedSection`
- `cheerio@1.2.0` — already installed in 5 workspace packages

## Architecture

### Data Flow
```
Content Generation (semantic patch + selector)
        │
        ▼
   Review Engine (approve / reject / edit)
        │
        ▼
   Execution Engine
        │
        ├─ fetchResource(pageId) → raw content
        ├─ domEngine.resolve(rawContent, patch) → patchedContent
        └─ provider.applyWrite({ ...operation, newValue: { content: patchedContent } })
```

### Key Types
- `PatchTarget` — discriminated union: `{ format: "elementor", elementId, settingsKey }` | `{ format: "gutenberg", blockPath, fingerprint, field }` | `{ format: "generic-html", resolvedSelector }`
- `PatchOperation` — JSON Patch verbs: `add | remove | replace | move | copy | test`
- `ContentNode` — generic tree node used by both Elementor and Gutenberg parsers
- `BlockFingerprint` — `{ hash: string; blockName: string; stableAttrs: Record<string, unknown>; siblingIndex: number }`
- `ResolvedSelector` — `{ selector: string; confidence: number; strategy: "attribute" | "text-anchor" | "structural" | "sibling" | "css" | "xpath" }`
- `PatchPreview` — `{ before: string; after: string; diff?: string; renderFidelity: "exact-html" | "structured-diff" }`

### Format Detection (`format-detector.ts`)
1. Non-empty `_elementor_data` post meta + `_elementor_edit_mode` = `elementor` (prefer active Elementor pages over stale meta)
2. Block comment delimiters in `post_content` = `gutenberg`
3. Else = `generic-html`

### Module Breakdown

#### `tree/` — shared structured-tree machinery
- `tree-node.ts` — `ContentNode` interface (id, type, settings, children, raw)
- `tree-patcher.ts` — JSON Patch ops against `ContentNode`; returns new tree
- `tree-differ.ts` — structural diff between two `ContentNode` trees
- `tree-validator.ts` — validates patch preconditions (`test` op)

#### `elementor/`
- `elementor-parser.ts` — `_elementor_data` JSON → `ContentNode` tree (preserves element `id` and `widgetType`)
- `elementor-serializer.ts` — `ContentNode` tree → `_elementor_data` JSON (lossless except targeted field)
- `widget-schema.ts` — maps widget types to settings keys (`heading` → `title`, `button` → `text`, `text-editor` → `editor`)
- `elementor-target-resolver.ts` — `{ elementId, settingsKey }` lookup, O(1)

#### `gutenberg/`
- `block-grammar-parser.ts` — comment-delimited grammar → `ContentNode` tree (state machine)
- `block-grammar-serializer.ts` — `ContentNode` tree → comment-delimited markup (save-format, not rendered)
- `block-fingerprint.ts` — `(blockName, stableAttrs, siblingIndex)` hash; path+fingerprint addressing
- `gutenberg-target-resolver.ts` — path match first, fingerprint fallback with confidence score

#### `generic-html/`
- `html-dom-mapper.ts` — cheerio-based section/block/hierarchy detection
- `selector-resolver.ts` — multi-strategy fallback (attribute > text-anchor > structural > sibling > CSS/XPath)
- `anchor-builder.ts` — text/sibling/heading/structural anchors
- `generic-target-resolver.ts` — resolves `ResolvedSelector` to cheerio selector with confidence

#### `patch/`
- `patch-engine.ts` — routes `PatchTarget` to correct resolver by format
- `patch-validator.ts` — enforces `test` preconditions before apply
- `patch-merger.ts` — merges multiple patches onto same tree (order: removes → adds → replaces)
- `patch-applier.ts` — orchestrates resolve → validate → apply → serialize

#### `preview/`
- `structured-preview.ts` — settings/attrs before-after diff (Elementor + Gutenberg)
- `html-preview.ts` — before/after/diff HTML (generic-html only)

## CLI Commands
```
forge dom map <pageId>        # detect format + dump ContentNode tree
forge dom preview <pageId> <patchJson>  # show preview with renderFidelity label
forge dom patch <pageId> <patchJson>    # apply patch, output patched content
forge dom validate <pageId> <patchJson> # run test ops + structural checks
forge dom inspect <pageId>              # format + tree summary
```

## Integration Points

### 1. Content Generation → Semantic Patches
- Extend `ContentPatch` with optional `semanticIntent?: { kind: string; value: string }`
- Writers populate `semanticIntent` when the patch meaning is unambiguous (e.g., `heading-text`, `button-text`, `faq-answer`)
- Existing `selector` + `operation` remain as fallback

### 2. Review Engine → Execution Engine (no change)
- Review sessions still produce approved items
- CLI `review apply` builds `ExecutionPlan` as before

### 3. Execution Engine → Dom Engine (new)
- Add optional `domEngine` parameter to `execute()`
- When present, for each action:
  1. `fetchResource()` to get raw content
  2. Call `domEngine.resolve(rawContent, action.payload.patch)` → patched content
  3. Set `operation.newValue = { content: patchedContent }`
  4. Call `provider.applyWrite(operation)` as before
- Provider stays format-agnostic; it just writes `newValue.content`

### 4. WordPress Provider (stub only)
- Add `applyDomPatch(resourceType, resourceId, domPatch)` stub that delegates to `applyWrite` with patched content
- Full `_elementor_data` REST integration deferred (needs custom WP plugin)

## Test Strategy
- **Elementor**: parse→patch→serialize round-trip byte-identical except targeted field (both legacy `section/column/widget` and `container` structures)
- **Elementor**: repeater/nested-widget content correctly rejected
- **Gutenberg**: grammar parse/serialize round-trip byte-identical for core blocks (paragraph, heading, image, columns, buttons)
- **Gutenberg**: fingerprint re-locates target after unrelated edit above it; reports low confidence / no-match when target removed
- **Format detector**: distinguishes active Elementor vs stale meta via `_elementor_edit_mode`
- **Generic HTML**: selector resolution priority (attribute > text-anchor > structural > sibling > CSS/XPath) with correct confidence scores
- **Patch engine**: `test` preconditions block invalid applies; `merge` handles overlapping patches deterministically
- **Preview**: `renderFidelity` correctly set per format

## Open Questions (resolved)
- **Q: Should dom-engine depend on content-generation?** A: Yes, import `ContentPatch` type. Keeps patch ownership in content-generation; dom-engine resolves, not owns.
- **Q: How does the execution engine pass patches to dom-engine?** A: New optional `domEngine` parameter on `execute()`. Action payload carries `patch: ContentPatch`; dom-engine resolves it against fetched content.
- **Q: What about the existing `selector` on ContentPatch?** A: Keep as fallback. New optional `semanticIntent` is preferred by dom-engine when present.
